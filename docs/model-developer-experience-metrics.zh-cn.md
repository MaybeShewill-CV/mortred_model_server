## Phase 2 catalog delta

After the task-local catalogs replaced the hand-written server registration
blocks, the deterministic digest changed to
`98c60f12aed9ce820f01eca6eb666da0c5e8d7a52416349fce7eef6d302650f7`.

| Metric | Phase 1 | Phase 2 |
|---|---:|---:|
| `factory_files` | 11 | 15 |
| `factory_lines` | 1154 | 1189 |
| `server_spec_blocks` | 22 | 1 |
| `model_section_assignments` | 22 | 3 |
| `server_section_assignments` | 22 | 1 |
| `fill_response_assignments` | 22 | 1 |

Reading the table: the single remaining `CvServerSpec` block lives in
`src/factory/cv_catalog.h` and is shared by every task. The 22 hand-written
per-model registration lambdas are gone; what is left per model is one explicit
catalog row (model section, display name, server section, worker creator,
response filler). Adding a served model now means adding that row plus the model
creator, instead of copying a registration lambda.

The catalog layer is deliberately split into two shapes:

- `models::catalog::ServedModelEntry` -> `factory::cv_catalog::CvModelEntry<OUTPUT>`
  for models mounted on the generic CV server (27 entries across 11 tasks).
- `models::catalog::ModelEntry` -> `factory::model_catalog::ModelCatalogEntry`
  for model families consumed directly by benchmarks and pipelines (CLIP,
  SAM predictor, FastSAM), which have no HTTP surface yet.

`test/model_catalog_unittest.cc` pins the contract: every entry is fully
populated, model/server sections are globally unique, the referenced TOML
sections and model config files exist, and `cv_catalog::create_server` really
instantiates a `CvModelServer<OUTPUT>`.
