# CV cowork

按 [workflow.md](workflow.md) 跑交付循环。评分标准是仓库根目录的 `cowork/ledger/rubric.md`。你是编排方。角色原文原样写入流程记录。模块分保持原文。加权分、上限和终态以你写的评分复核为准。

| 步骤 | subagent | 写权限 |
| --- | --- | --- |
| 1 评分；2 修订列表并确认；7 关闭 | `cv-cto` | 只读 |
| 2 评审并确认；3 审查确认 | `cv-pm` | 只读 |
| 2 评审并确认；3 起草方案并确认；4 实现偏差确认 | `cv-tech-lead` | 只读 |
| 3 确认；4 实现和自测 | `cv-rd` | 第 3 步不改文件；第 4 步只改当前 worktree |
| 5 测试 | `cv-qa` | 只改该 worktree 的测试 |

这些角色只在本技能派到该步，或用户点名 `/cv-cto`、`/cv-pm`、`/cv-tech-lead`、`/cv-rd`、`/cv-qa` 时使用。自定义 subagent 不可用时停下来，说明需要新开一轮。不要用通用子代理代替。

## 开工条件

基线分支是 `sub-agent-co-work`。`git status --porcelain` 非空时停下来，列出未提交文件，等用户处理。不要 stash，不要把无关改动带进问题分支。

流程记录在 `cowork/ledger/`。先读 `index.md`。当前执行从第 1 轮第 1 步开始，新记录直接写入 `cowork/ledger/round-NNN/`。不要写入 `cowork/ledger/active/`，也不要在别的目录另建一份流程记录。不要把 git 历史里的旧轮次检回工作区，不从中继承队列、已关闭 id、分数或阻塞项。每次角色返回后、你写流程记录前，再跑一次 `git status --porcelain`。基线出现角色改动就停止，不提交那些改动。

流程记录只在基线分支提交，路径只限 `cowork/ledger/`。实现和测试只在问题分支提交。提交说明写清轮次、步骤和问题 id。不提交密钥、`conf/local/`、权重和无关改动。

## 复核

模块调用彼此独立，不要 resume。每次提示词带上 rubric 的绝对路径、模块 id，以及 `cv-cto` 里该模块的必读路径。

九份模块记录齐了之后，用 rubric 的权重计算原始分：各模块（分数 × 权重）之和 / 100，保留一位小数。权重只取 rubric。还有未关闭且未阻塞的 P0 时，加权分不超过 7.9；还有这种 P1、没有这种 P0 时，不超过 8.9。阻塞项不触发上限。把结果写入 `01-score-check.md` 或 `07-score-check.md`。角色自评分数不一致时，在评分复核里写明，状态机采用评分复核。模块记录存在未覆盖路径且分数高于 8.0 时，退回该模块，不进入加权分。问题缺少出处、现在的行为或一次外部验收即可确认的变化时，退回该条，不进入第 2 步。已关闭 id 的问题陈述仍留在开放项里时，退回该记录。满足入列条件却没有出现在 P0、P1、P2 或阻塞项里的，退回，不进入第 2 步。

终态由评分复核决定，不采用角色正文里的终态说法。评分复核必须按 rubric 的「完成标准」逐行写「已满足 / 未满足 / 阻塞」。`done`：每一行都是「已满足」，九份模块的开放项都是「无」，且阻塞项为空。`awaiting-env`：没有「未满足」，未阻塞的开放项都是「无」，但仍有阻塞项。加权分只作记录。没有未关闭入列项时，问题写「无」，分数可以低于 9.0。完成标准有未满足行时，不得把问题写成「无」。

## 循环

评分标准没变时，上一轮关闭后的队列就是下一轮的起点。已确认且未关闭、未阻塞的 id 原样进入下一轮，从第 3 步继续，不再评审。只有新 id 才走第 2 步。git 历史里的旧轮次不构成上一轮。本序列从第 1 轮第 1 步开始，记录在 `cowork/ledger/round-001/`。轮次上限是 20。进入第 21 轮前停止。

1. **评分。** 按 rubric 的模块顺序逐个调用 `cv-cto`。每个模块一份 `01-modules/<id>.md`。九份都通过未覆盖检查和入列检查后，再让他写 `01-score.md`，然后你写 `01-score-check.md`。已有锁定队列的轮次跳过本步。
2. **锁定交付范围。** 队列含 P0、P1，以及达不到这两档、但仍满足入列条件的 P2 项。已确认且未关闭、未阻塞的 id 原样保留，不再评审。只对新 id 做三步：PM 和技术负责人并行评审；CTO 只返回 `列表修订`；PM、技术负责人和 CTO 再并行返回 `第2步确认`。通过条件是三份确认的 `针对版本` 相同，且 `结论` 这一行的值都是 `同意`。否则把不同意的理由交给 CTO 修订下一版。新 id 最多两轮。仍不通过时，立刻给出决策选项，不要只把状态写成 `stopped` 后停住。每个选项是一版列表正文，选项文字使用该版里待决定条目的「改完后能观察到的变化」。另加一项「停止本轮」。用户选定一版后，把该版写入 `02-p0-p1-final.md`，在文末记下用户决定和未被选中的原文，状态保持 `running`，并继续第 3 步。不再为同一列表开第三轮确认。用户选择停止时，才把状态写成 `stopped`，并把尚未通过的原文交给用户。通过后写入 `02-p0-p1-final.md`。本轮队列已经锁定时，跳过本步，从第一条未关闭且未阻塞的问题进入第 3 步。一次外部验收确认不了的句子，在锁定前拆成有限清单，或移入范围外并写入附录。满足入列条件的 P2 不得因为不够 P0 或 P1 而被删掉。重复描述写入附录，不留在 P2 里。
3. **一个问题一份方案。** 先未关闭且未阻塞的 P0，后 P1，再 P2，一次一条。阻塞项跳过。已有 `03-design-final.md` 且三方确认仍有效的问题，不重开方案，直接进入第 4 步。技术负责人先返回方案正文。PM 和 RD 并行确认。有 `不同意` 时，技术负责人把条件写进下一版本正文，版本号加一。然后三方对这一版分别确认。通过条件是三份 `方案版本` 相同，`结论` 都是 `同意`，`条件` 都是 `无`。最多两个版本。仍不通过时，立刻给出决策选项，不要只把状态写成 `stopped` 后停住。每个选项是一版方案，选项文字使用该版「边界」里的可观察行为。不同意方的条件如果要求的是另一套可观察行为，单独列成一个选项。另加一项「停止本轮」。用户选定后，把选定正文写入 `03-design-final.md`，在文末记下用户决定、选用版本和未被选中的条件原文，状态改为 `running`，进入第 4 步。不再为同一问题开第三版确认。用户选择停止时，才把状态写成 `stopped`，并把尚未通过的原文交给用户。三方通过后同样写入 `03-design-final.md`。第 3 步每次调用返回后都检查基线工作区。
4. **实现。** 从当前基线创建分支 `cowork/r<轮次>-<问题id>-<短名>`，用 `git worktree add` 放到仓库外的目录。已有问题分支且实现偏差为「无」时，沿用该分支，不另开方案。RD 在这个 worktree 里实现、自测，并在问题分支上提交。提交里要能看到相对基线的代码变更。`实现偏差` 不是 `无` 时，先让技术负责人返回 `实现偏差确认`。`不同意` 就退回 RD 改回方案。不在这一步合入。
5. **测试和合入。** QA 在同一 worktree 按方案测试。有测试改动就在问题分支上提交。你在该 worktree 重跑报告里的每条命令，退出码要和报告一致。报告是 `pass`、每条验收标准都有一行、重跑一致、问题分支相对基线有提交、且基线工作区干净时，在基线上执行 `git merge --no-ff <分支>`。把命令和 merge commit 写入 `05-merge.md`，再把流程记录提交到基线。合入记录写完后删除该 worktree，并删除这次问题留下的无用脚本。`fail`、退出码不一致、冲突，都不合入。`fail` 时 RD 在原分支修，最多两个来回。RD 认为缺陷来自方案时，技术负责人只改冲突的一节并把版本加一，这个修订最多一次，三方必须对新版本重新确认。`blocked` 不合入，也不停止本轮。写入 `05-suspend.md`，写明缺的环境、恢复条件和未跑的验收编号，然后删除该 worktree 和无用脚本，再继续下一条。阻塞不消耗失败次数。该问题因失败或停止不再继续时，同样删除当时的 worktree 和无用脚本。
6. **收口。** 从 RD 的「新增问题」和 QA 的「残余风险」里，把当前列表以外、且满足入列条件的问题写入该轮 `discovered.md`。不写入产品 worktree。重复描述和一次外部验收确认不了的句子写入附录，不插入当前队列。除阻塞项以外的队列都已合入或移入范围外后，进入第 7 步。本轮只要有新的合入，就对已合入且尚未关闭的项做第 7 步，不等待阻塞项。
7. **关闭。** 把已合入 id、各自绑定的问题陈述、阻塞项、`discovered.md` 和 diff 路径摘要交给 `cv-cto`，只要 `关闭记录` 模板。已关闭的问题陈述必须从开放项删除，重复描述放附录。新入列项只接受满足入列条件的新证据。你核对后写入 `08-writeoff.md`，并重写 `07-score-check.md`。已关闭的问题陈述仍留在开放项里，就退回，不进入下一轮。

## 停止

把索引状态写成 `stopped`、`done` 或 `awaiting-env`，并把评分复核和尚未通过的原文交给用户：

- 完成标准每一行都是「已满足」，开放项都是「无」，且阻塞项为空。状态写 `done`。
- 没有「未满足」，未阻塞的开放项都是「无」，阻塞项非空。状态写 `awaiting-env`。环境恢复后从该问题分支重新 `git worktree add`，只重跑阻塞项的第 5 步，通过则合入并关闭，然后再次删除该 worktree 和无用脚本。
- 本轮有未阻塞项合入或移入范围外，但关闭后未阻塞的开放项一条都没减少，且没有任何完成标准行从「未满足」变成「已满足」。状态写 `stopped`。
- 队列或方案的两轮确认仍未三方同意。先按上面的决策选项让用户选定一版并继续。用户选择停止时，状态写 `stopped`。
- 实现偏差、自测或 `fail` 回修超出上面的次数，基线工作区出现计划外改动，重跑结果和报告不一致，或 merge 冲突。`blocked` 不在此列。
- 当前轮次已经是 20，并且本轮该做的关闭已经写完。不得进入第 21 轮。状态写 `stopped`。

不要 force push，不要硬重置，不要跳过 git hooks。

## 运行环境

本机 WSL 的默认发行版 Ubuntu 提供 GPU 和 Mortred 的 runtime。构建、prepare、calibrate、拉起、压测，以及需要 GPU 的自测和测试，都在这个 WSL 里执行。仓库在 WSL 中的路径是 `/mnt/g/Codex/mortred_model_server`。流程记录写回 `G:\Codex\mortred_model_server\cowork\ledger`，不要在 WSL 家目录另建记录。

当前 shell 是 Windows 时，先进入该 WSL 再跑上述命令。不得因此把性能、吞吐、engine 或占用标成阻塞。只有在 WSL 里确认缺少 GPU、权重或服务时才标阻塞，并写明 WSL 里缺什么。

## worktree

问题实现和测试使用仓库外的 worktree。这棵树在合入记录写完、阻塞记录写完，或该问题停止并不再使用它之后删除。在基线仓库执行 `git worktree remove <path>`。树上还有未提交的产品改动时停下来交给用户，不要 `--force`。

无用脚本是这次问题新建的、没有出现在合入提交里的脚本。删除 worktree 之后把这些文件删掉。合入提交里的脚本，以及仓库里原本就有的 `scripts/`，保留。
