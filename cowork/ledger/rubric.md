# 落地评分口径

自 2026-09-30 起，出口改为九个模块的劣势都是「无」。权重和模块不变。此后循环期间不改权重、不改模块、不改下面的问题定义、不计毛病和出口。综合分按本文件计算，只作记录，不决定出口。

评分人是已经在中小企业 Linux 服务器上使用 Mortred 的 CTO。分数表示：这个模块让小团队拿去交付客户项目时有多能用。0 是无法使用，10 是小团队可以独立交付并在出错时定位。

## 模块

| id | 路径 | 权重 |
| --- | --- | --- |
| src-models | `src/models` | 15 |
| src-server-apps | `src/server`、`src/apps` | 15 |
| src-control | `src/control` | 10 |
| src-factory-common | `src/factory`、`src/common` | 5 |
| conf | `conf/` | 10 |
| ops | `scripts/`、`deploy/`、`mortredctl` | 15 |
| test | `test/` | 15 |
| docs | `docs/`、`README.md`、`README.zh-cn.md` | 10 |
| ci | `.github/` | 5 |

九个模块都要有独立记录。没读过的模块不能打分，也不能从分母里去掉。

模块分取 0.0 到 10.0，保留一位小数。低于 9.0 必须写出劣势。每条优势、劣势和分数都要有文件、命令或测试出处。没有出处的分数无效，综合分不得计算。

加权综合分 = 各模块（分数 × 权重）之和 / 100，保留一位小数。

## 问题

P0：现有接法让一次客户交付发不出去，或出了错无法定位。

P1：能交付，但每上一个模型、换一台机器都要重复一套易错手工步骤。

交付范围内的每一条劣势都进入实现队列。达不到 P0 或 P1 的，列入「劣势」，编号 D-1、D-2。同一类痛点并成一条。旧问题改写不进入队列。

## 不计毛病

下列内容不写成模块劣势，不进入实现队列，可以记在附录：

- `docs/unsupported-boundaries.md` 列出的不支持项，包括 HTTP OCR 只有检测、没有识别。
- 一个 catalog id 一个 OS 进程。超时 drain 之后析构成员，再由外层 SIGKILL。
- 训练平台、标注平台、多云平台。
- 没有真实交付损失就推翻 HTTP 契约或现有后端。

## 上限

最终列表里还有 P0 时，综合分不得超过 7.9。还有 P1、没有 P0 时，综合分不得超过 8.9。先按权重算出原始分，再套上限。这些上限不代替出口。

## 出口

九份模块记录的「劣势」都是「无」。综合分只作记录。

劣势集合是九份模块「劣势」节里的条目，不含附录里的不计毛病。本轮复审后的集合相对本轮起点没有减少任何一条，循环停止。
