## 附录

v1 的 P1-1 拆成两条：P1-1 是 gateway 阶段耗时默认可读；P2-11 是九个 TensorRT id 的 calibrate 与 `--raw` 报告清单。PF2、PF5 随这张清单勾销，不另开条目。

P2-3 的通过条件是这一次启动里 fork 出的子进程上的一次库函数跟踪（ltrace 或等价工具）。`fork` 返回之后、随后的 `exec` 之前，跟踪里出现的库函数名没有 `prctl`、`execvp`、`setenv`。带绝对路径的 `execve` 可以作为随后那次 `exec` 本身出现，不算失败。下面两句不作为通过条件。只对照源码确认 `src/control/supervisor.cpp` 拉起模型子进程，以及 `src/control/gpu_sampler.h`、`src/control/occupancy_gate.h` 两处 `nvidia-smi` 探测，在 `fork` 与 `exec` 之间不出现 `prctl` 和 `execvp`。把 `nvidia-smi` 改为带绝对路径的 `execve`。

P2-7 不作为通过条件的结果：成功返回增强图，且送入会话的形状为 `1×256×256×3`。

原 P2-8 整条从队列删除。交换目录不是调用路径。`docs/unsupported-boundaries.md` 把 `conf/onnx_sources.json` 定为 ONNX 交换、合同和许可证的依据，engine 不能当 ONNX 交换物。

v2 的 P2-3「改完后能观察到的变化」：对这一次启动 fork 出的子进程做一次系统调用跟踪。跟踪里，`fork` 返回之后、随后的 `exec` 之前没有 `prctl`、`execvp`、`setenv`。同一次启动后模型子进程处于运行，`nvidia-smi` 探测有输出，或按现有规则标明失败。

v2 的 P2-11 通过条件中多出的一句：引擎保持 static shape、batch=1，每个 worker 仍各自持有 TensorRT execution context。

未被选中的另一套可观察行为：同一次库函数跟踪必须写出随后那次 `exec` 的函数名。`nvidia-smi` 探测只有在这次调用是带绝对路径的 `execve` 时才算通过；若是 `execvp` 则不通过。这次 `exec` 之前没有 `prctl`、`setenv`。只去掉模型子进程里的 `prctl` 不算通过。
