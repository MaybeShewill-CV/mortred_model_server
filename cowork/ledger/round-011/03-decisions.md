# 本轮评估期间的决策记录

## D1（2026-10-19）暂不做显存节省方向的工作

- **决定**：S1（TRT 引擎进程内共享 / 每 worker 一个 context）、S2（GPU 解码槽池）**暂缓**，不进入实施。
- **理由（用户判断）**：共享会牺牲 RPS 吞吐，得不偿失；当前阶段吞吐优先于显存利用率。
- **技术备注（供将来重开时参考，不构成反驳）**：
  - 共享 `ICudaEngine` 本身不改并发语义（context 仍按 worker 各一），TRT 官方多流模式即 1 engine + N context；若重开须用 **ABAB 交错 12 次取中位数** 判定 RPS/p99，因为本机同一命令三次实测为 424 / 613 / 652 RPS（方差 ±30%），单次对比无法区分噪声与回归。
  - 收益集中在 300–640 MiB 的大型 TRT 引擎（`depth_anything_vitl14` 642 MiB、`dinov2_vitl14` 583 MiB）；对 14–24 MiB 的小引擎收益可忽略。
  - **实施前必须先做零代码改动的前提验证**：`worker_nums=1` vs `=8` 两次启动对比 `nvidia-smi memory.used`，确认"N 份引擎"是否真实存在；若差值远小于 (N−1)×引擎大小，说明已有复用路径，S1 直接放弃。
- **不受此决定影响（仍在范围内）**：S3（tokenizer 单例，省 host 词表内存，不涉显存）、S4（ORT session 共享，本来就要先测且默认不做）。

## D2（2026-10-19）"模型 /metrics 拒绝抓取凭据"降级为配置歧义

- 上一版评估把它写成"r13 的修复被 r14 的 allowlist 抵消（回归）"，**该结论错误**。
- 事实：`src/control/supervisor.cpp:493-495` 会把 `MORTRED_METRICS_TOKEN` 注入模型子进程（注释即写明用途）。
- 我实测 401 的真实原因：**同一用途存在两把不同的 48 字符令牌**——`conf/local/trust.env` 的 `MORTRED_METRICS_TOKEN` 与 `conf/local/mortred_metrics_token` 内容不同（SHA 不同），而 supervisor 使用的是后一路来源。
- 因此问题性质为**凭据来源歧义**（运维无法判断该用哪把），不是功能失效。修法候选：统一来源，或在两者不一致时 fail-closed 拒绝启动。
