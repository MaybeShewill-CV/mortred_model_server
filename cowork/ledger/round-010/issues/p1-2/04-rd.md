## 行为变化

1. `supervisor_app.cpp`：删除 `::setenv("MORTRED_API_TOKEN", auth_token_, 1)`。该调用冗余——同一个 `auth_token_` 已由 `set_gateway_trust(options.metrics_token, options.gateway_auth_token, auth_token_)`（`:854`）交给 supervisor 的 `_gateway_admin_token`，gateway 分支随后显式注入 `MORTRED_API_TOKEN`（`supervisor.cpp:418`）。保留了 CORS-origins 的 `setenv` 并重写注释说明"凭据不走进程环境，CORS 是 gateway-only 且模型侧无害"。
2. `supervisor.cpp`：新增 `drop_env_entry()`（紧邻 `override_env_entry()`，`:61`，按 `key + "="` **精确匹配**，不会误删前缀相同的键）；`spawn_locked` 在 environ 拷贝之后（`:403-406`）、`::fork()`（`:462`）**之前**统一删除 `MORTRED_API_TOKEN` / `MORTRED_METRICS_TOKEN` / `MORTRED_GATEWAY_AUTH_TOKEN` / `MORTRED_INTERNAL_TOKEN`，随后既有分支注入照旧：gateway 分支重新注入 internal/scrape/infer/admin 四键（`:408-419`，即"删→注入"顺序正确），模型分支一个都不注入（只注入 `MORTRED_AUTH_TOKEN=internal_token`、`MORTRED_LISTEN_HOST=127.0.0.1` 等）。
3. 净效果：操作者 shell / systemd `EnvironmentFile` 里的管理/scrape 凭据不再随整份 environ 进入任何被管子进程；模型进程不再持有管理 bearer。

未改：supervisor/gateway 的 token 校验与 `trust_tokens` 文案、`set_gateway_trust` 契约、argv/catalog 契约、环回"零 token 允许"行为、`MORTRED_GATEWAY_CORS_ORIGINS`；未用 `clearenv`；`fake_model_server.cc` 未改（不需要）。

## 测试实现取舍（不改变契约）

- (a) 子进程存活改由用例内 `write_fake_config("ready", 60000)` 显式重写配置，而不是依赖 `SetUp` 的 `exit_after_ms=0`（永不退出）。
- (b) gateway stub 起初用 `#!/bin/bash\nexec sleep 3600`，结果 gateway 停在 `state=starting … error=`（`sleep` 不应答 `/healthz`，就绪探测不通过）；改用 fixture 既有的 `install_gateway_stub("ready")`（bash 包装 fake 二进制应答 `/healthz`）后即 `running`。这顺带证明了 bash 包装 exec 之后 `/proc/<pid>/environ` 仍反映 `spawn_locked` 传入的 envp。

## 新增问题

无阻塞项。两点供记录：

1. **不是缺陷但值得注意**：模型子进程仍持有 `MORTRED_AUTH_TOKEN=<supervisor internal token>`（方案明确的保留项，gateway 用同一个 `_internal_token` 调模型）。因此若操作者把 `MORTRED_INTERNAL_TOKEN` 当作"只给 gateway 的秘密"复用，模型侧仍能看到该值——那是内部令牌的既有契约，本轮不动。
2. **验证覆盖边界**：该 worktree 的 cpu profile 不产出 gateway/模型真二进制，故 A3 只能在 QA 的完整部署里闭环；`install_gateway_stub` 的 bash 包装路径已证明 `/proc/<pid>/environ` 在 exec 后仍反映 `spawn_locked` 的 envp，故 A1 的 gateway 侧断言对真 gateway 同样有效。
