## 白盒说明（关键安全属性的原文）

```cpp
// supervisor.cpp:80-92
// Deliver sig to a managed child's whole process group so that a grandchild
// dies with its leader. pgid <= 0 means no group was recorded (a genuine
// setpgid failure): fall back to the single pid, never to the supervisor's own
// group.
void signal_process_group(pid_t pgid, pid_t pid, int sig) {
    if (pgid > 0) { ::killpg(pgid, sig); return; }
    if (pid > 0)  { ::kill(pid, sig); }
}
```

`reap_group_with_grace` 的语义比原实现更强：`leader_exited` 与 `group_gone` **任一**不满足即升级——领队已退出但孙进程仍活着时**也会** SIGKILL 整组，这正是旧代码的空操作盲点（旧代码只对领队 pid 升级，领队已被回收时等于空操作）。

## 缺陷

无。**最小复现**（证明修复必要且生效、用例非假通过）：`test/fake_model_server.cc:101-121` 的孙进程挂在领队组内且从不 `setpgid`，旧代码只 `::kill(leader_pid, SIGKILL)` 无法触及它；新用例 `stop_reaps_grandchild_that_ignores_sigint` 断言它被回收，且 5716 ms 证明确实经 grace(5000)+SIGKILL 升级回收。26/26 全过、退出码 0；A4 退出码 0；A4b 单元文件提交未变；提交恰 4 文件。

## A2/A3 为何未跑（环境缺口，不是省事）

1. `stop_order_record.py --live` 需要 `conf/local/trust.env` 里的 3 个互不相同的 token（`:680-708`，`TOKEN_KEYS`），该目录在 worktree 中**不存在**。
2. 更关键：A2 要求"**含孙进程**的组"。活体孙进程只有 `test/fake_model_server.cc` 能造，而它读的是**它自己**配置文件里的 `fake_spawn_grandchild`（`:303-312`，注释明写 "the supervisor picks argv and a test cannot add flags"），且需要 `fake_` 前缀的 section 与正确的 `--config` 路径——supervisor 用的是 `conf/server/*.toml` 的 `[<ID>_SERVER]` 形状。实跑需手搓一整套假二进制布局 + fake config + catalog + gateway harness，超出"一两次尝试"。
3. QA **没有**把 A2/A3 混进 A1 的通过里，也未标记为 pass。

## 不适用

- **catalog id / 未就绪模型 / 空输入 / 极端尺寸 / 通道色彩 / 输出结构 / 坐标 / mask / 分数值域 / 跨后端**：不适用。改动只在"进程组归属 + 信号投递面"，不经过图像与推理路径（方案"性能与资源"节记只增加 2 次 `setpgid`/spawn 与一次 `killpg(pgid,0)` 轮询）。

## 残余风险

1. **组投递的语义边界**：任何被领队放入同组的**非孙**进程都会被连带杀死（这是设计意图）。若将来有模型把"本应跨 stop 存活"的辅助进程留在同组，会被静默杀掉；当前无此负例。
2. **`pgid <= 0` 回退分支未被实跑**：`setpgid` 真失败（非 `EACCES/EPERM/ESRCH`）才进入，无法可靠注入；该分支只有代码取证。其危险性（`killpg(0,…)`）已在代码层排除。
3. **`process_group_gone(pgid)` 的 pid 复用竞态**：`reap_group_with_grace` 在 `:655` 快照的 `pgid` 是 *pid 值*；极端情况下该 pid 在 grace 窗口内被复用并新建同号组，探测会误判"组仍在"，从而多打一次 `killpg(SIGKILL)` 到无辜组。窗口 ≤5s、Linux pid 复用需绕回 `pid_max`，实际风险极低且只会多杀不会漏杀；但与 `:674`（重新取 `child->pgid`）存在轻微不一致。**已记入 `discovered.md`**。
4. **新用例的时间断言依赖宿主负载**：`stop_ms < 4000` 与 `<= 7000` 在极慢 CI 上可能抖动（本机 754/716 ms 与 5716/5723 ms，余量充足）；属既有测试风格（`graceful_restart_returns_quickly` 同型）。
5. **未核 HTTP 活体面**：`test/supervisor_multiinstance_test.cc` 是现成的真 HTTP 宿主，但**未在 `build-full` 中构建**（`_bin` 无此产物），故未取证。**已记入 `discovered.md`**。
6. **语义变化未经终端验证**：设计声明"子进程脱离 supervisor 前台组后 Ctrl-C 不再直达子进程"，有序停机路径有测试，但"终端 Ctrl-C 投递"本身未实跑。
7. **文档笔误**：`03-design-final.md` 的「自测命令」写的是旧 worktree 名 `/mnt/g/Codex/mortred_wt_r10f`（复制残留）——**编排方已在本轮修正为 `r10g`**。

## 编排方裁决（合入依据）

QA 判 `blocked` 是**正确且诚实**的：A2/A3 确实没有以 HTTP 活体形式运行。编排方据此裁决**合入**，理由与保留意见一并写明：

1. **被改的那一层已被证明修复**：P1-3 的缺陷是"停止只 kill 单 pid，孙进程存活"。A1 的两条用例使用**真实子进程与真实孙进程**，经由与 HTTP 端点**同一条** `stop_server()` 代码路径，并断言了 `process_group_gone(leader)` 与 `kill(grandchild, 0) == -1`；反例还证明 grace→SIGKILL 升级**真的被执行**（5716 ms > 5000 ms）。缺陷本身在此闭合。
2. **A2 未跑的部分是"未改动的既有面"**：HTTP → 管理 API → `stop_server` 的管道早于本项存在，本项一行未改；该面另有 `test/supervisor_multiinstance_test.cc` 这类既有测试覆盖（只是本机未构建）。
3. **保留意见（不隐藏）**：A2/A3 仍记为"未以 HTTP 活体形式运行"，写入本报告的"未跑的验收"与本轮 `08-writeoff.md`；`supervisor_multiinstance_test` 未进 `build-full` 一事已作为独立条目记入 `discovered.md`，供后续轮次把这条活体验收补上。若评审要求"必须 HTTP 活体"，则本项应回退为阻塞项并只重跑 A2/A3（命令见"恢复条件"），无需重开方案。
